# 4-DN-36-O1 UI&UX 제약사항

> `TBD`·`[확인 필요]` 항목은 승인 전 채운다 — 이 활동이 닫을 수 없는 것은 조건부 승인의 조건으로 남긴다(`9-CM-01` 「초안 표기」). `—` 는 해당 없음을 의도적으로 명시한 것이다.
> 범례: `○` 허용 / `—` 해당 없음 / `△` 조건부(비고에 조건 명시) / `×` 명시적 비허용
> 제약 등급: 상류 `Must` 요구사항·확정 예외 흐름·보안·인가 규칙에서 직접 나오면 `Must`, 미충족이 요구사항 위반을 낳지 않으면 `Should` — `Must`는 승인과 함께 동결된다(품질 게이트 dn-36.P7)
> CRUD 셀은 **서버 영속 연산** 기준이다 — 저장 전 화면 안에서만 처리하는 동작(첨부 스테이징 제거·위저드 단계 취소 등)은 서버 연산이 없으므로 `—`로 두고, 그 동작은 같은 화면의 제약 표에 적는다(API 명세서 작성(`5-IM-12`) 게이트 im-12.P4가 `○`·`△`에 operation을 요구한다).

> **이 문서의 확정은 화면을 만들기 전의 명세 확정이다.** 4-DN 완료 게이트는 전체 화면 시안(`4-DN-38-O1`) §1의
> PL 승인이며, 계약상 설계 검수는 설계 검수 조서(`4-DN-38-O2`)로 따로 간다. 다만 여기서 무엇이 확정되고 무엇이 뒤에 남는지를
> 밝혀 두어야 나중에 범위 분쟁이 없다.
>
> | 이번에 확정하는 것 | 이번에 확정하지 않는 것 |
> |---|---|
> | 화면별 CRUD 범위·업무 제약·메시지 문구·셀렉트박스 항목 (**Must 항목은 동결**) | 화면의 시각적 완성도. 실제 화면은 전체 화면 코드베이스 통합(`5-IM-11`) 프로토타입에서 확인한다(발주처 컨펌 ②) |
>
> 톤앤매너·레이아웃은 이 문서의 확정 뒤 전체 화면 시안 작성(`4-DN-38`) 발주처 컨펌 ①에서 확인하며 이 문서의 대상이
> 아니다. 두 게이트의 성격 구분은 워크플로 가이드(`4-DN-00`) 「발주처 컨펌 공통 규정」 (4)를 따른다.

## 2. 전역 규칙

> **[작성 안내]** 화면 유형과 무관하게 **모든 화면이 공유하는** 제약과 상태 메시지를 여기서
> 한 번 정의한다. 화면별 절(§3 이하)에는 **그 화면에만 있는 것**만 적는다 — 같은 내용을
> 화면 수만큼 복제하지 않는다. 일부 화면에만 걸리는 공통 규칙도 여기 한 번 정의하되 **대상 화면을
> 열거하지 않는다** — 대상은 그 제약 ID를 인용한 화면 절이 정한다(열거는 화면 절이 늘 때마다 거짓이 된다).
