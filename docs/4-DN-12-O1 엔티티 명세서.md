## 2. YAML 구조 기준

`entities.yaml`은 최상위에 `meta`(문서 메타) · `entities`(엔티티 목록) · `value_objects`(가치 객체 목록, 있는 경우) 세 키를 둔다.

> `entities.yaml` 머리에 `meta:` 블록(키·규약은 DOC-TEMPLATE(`9-CM-01`) 「산출물 문서 메타」). 산출물 ID는 `4-DN-12-O2`이며 `4-DN-12-O1`과 별개로 확정한다.

각 엔티티는 아래 항목을 포함한다.

| 항목 | 설명 |
|------|------|
| `name` | Java 클래스명 (PascalCase) |
| `table` | DB 테이블명 (snake_case, 프로젝트 접두어 포함) |
| `ent_id` | 도메인 분석표 또는 도메인 정의서(4-DN-11)의 ENT-ID (추적성 확보. 설계에서 신설된 엔티티는 도메인 정의서 ID를 쓴다) |
| `bounded_context` | 소속 Bounded Context |
| `aggregate_root` | Aggregate Root 여부 (true / false) |
| `origin` | 출처 `신규` / `편입` / `변경`. `편입`은 기존 시스템 편입(`1-PN-02`)이 DB 스키마에서 역추출한 엔티티(코드가 정본 — Backend 코드 구현(`5-IM-24`) 게이트 im-24.B3 방향 반전 조건), `변경`은 편입 뒤 근거 REQ `범위`가 `기존`→`구현`으로 바뀌어 이번에 고치는 엔티티. 신규구축은 전부 `신규`이며 생략 시 `신규`로 본다 |
| `req_ids` | 근거 REQ-ID 목록. `편입`·`변경` 엔티티의 전환 대조 자리 — 요구사항 `범위`와 `origin`은 서로 다른 판정을 가질 수 있다(`get_rule("skip")` 0번). 신규구축은 생략 가능 |
| `fields` | 필드 목록 |
| `fields[].name` | Java 필드명 (camelCase) |
| `fields[].column` | DB 컬럼명 (snake_case) — `embedded:` 필드는 생략하고 VO `fields[].column`이 컬럼명이다. 같은 VO를 한 엔티티가 둘 이상 임베드하거나 이름이 충돌하면 `column_prefix`를 둔다(`[JPA]` `@AttributeOverride`, `[SQL 매퍼]` 결과 모델 접두) |
| `fields[].column_prefix` | (선택) `embedded:` 필드의 VO 컬럼명 앞에 붙는 접두(예: `billing_`) |
| `fields[].type` | Java 타입 (Long, String, LocalDateTime, BigDecimal 등) — `embedded:`와 배타(둘 중 하나만 쓴다) |
| `fields[].embedded` | 이 필드가 `value_objects`의 VO 하나를 통째로 참조할 때 그 VO명을 적는다. `[JPA]` `@Embeddable`/`@Embedded`, `[SQL 매퍼]` 다중 컬럼 결과 모델로 반영된다(`5-IM-06` im-06.P2가 판정) |
| `fields[].pk` | PK 여부 (true / false) |
| `fields[].nullable` | null 허용 여부 (true / false) |
| `fields[].unique` | UNIQUE 제약 여부 (true / false) |
| `fields[].length` | 최대 길이 (String 타입만, 없으면 생략) |
| `fields[].default` | 기본값 (없으면 생략) |
| `fields[].description` | 필드 설명 및 관련 BR-ID |
| `relations` | 연관관계 목록 |
| `relations[].type` | 관계 타입 (ManyToOne, OneToMany, OneToOne, ManyToMany). 이름은 JPA 어노테이션과 같지만 **영속성 기술과 무관한 논리 관계**다 — JPA는 어노테이션으로, SQL 매퍼는 FK 컬럼과 `resultMap` 중첩으로 구현한다 |
| `relations[].target` | 대상 엔티티 클래스명 |
| `relations[].fk_column` | FK 컬럼명 |
| `relations[].cardinality` | 카디널리티. 기본 표기(1:1, 1:N, N:1, N:M) 외에 옵셔널 표기(`0..1:N`, `1:0..1` 등)를 허용한다 — 이는 **관계의 최소 개수 제약**이며, FK 컬럼의 NULL 허용 여부는 `fields[].nullable`이 정본이다. 둘이 어긋나면 `nullable`을 따른다 |
| `relations[].name_ko` | 한글 관계명. 4-DN-11 수행 시 도메인 정의서(`4-DN-11-O1`) §4를 그대로 옮기고, 생략 시 도메인 분석표(`3-AN-05-O1`)의 `관계명`을 계승해 여기서 확정한다 — 클래스 다이어그램 작성(4-DN-13) 클래스 다이어그램·테이블 구조 설계(4-DN-14) ERD 관계 라벨의 정본 |
| `relations[].name_en` | 영문 관계명. `name_ko`에 대응하는 lowerCamelCase 동사구(`주문한다` → `places`) |
| `relations[].rel_id` | 도메인 분석표의 REL-ID(`REL-NN`) 또는 도메인 정의서(4-DN-11)가 설계에서 신설한 REL-ID(`REL-D01` 형식). 분석 번호를 이어받아 신설하지 않는다 — 도메인 분석표 개정 시 충돌한다 |
| `business_rules` | 연관 BR-ID 목록 |

`value_objects`는 엔티티와 나란한 최상위 목록이다. 식별자 없이 값으로만 동등성이 판별되는
개념(금액·기간·주소 등)을 여기 정의하고, 엔티티 `fields[]`에서는 `embedded:`로 참조한다.

| 항목 | 설명 |
|------|------|
| `name` | VO 클래스명 (PascalCase) |
| `fields[].column` | VO 필드의 DB 컬럼명 — 엔티티 측 `column_prefix`가 있으면 그 뒤에 붙는다 |
| `owner` | 이 VO를 처음 정의한 소속 엔티티명(문서화 목적 — 여러 엔티티가 같은 VO를 `embedded`로 재사용할 수 있다) |
| `fields` | 필드 목록 — 엔티티 `fields`와 같은 구조(`name`·`type`·`length`·`description` 등). `pk`는 없다 |

## 3. YAML 예시

이 프로젝트의 정본은 `entities.yaml`(`4-DN-12-O2`)이다. 중복을 피하려고 YAML 전문을 이 문서에 옮기지 않고 요약만 둔다.

| ENT-ID | 엔티티 (`name`) | 테이블 | Bounded Context | 관계 (`rel_id`, 관계명) | 연결 BR |
|--------|----------------|--------|-----------------|------------------------|--------|
| ENT-01 | MeetingRoom | `meeting_room` | 회의실 | REL-02 `예약을 받는다` (→ Reservation, 1:N) | — |
| ENT-02 | Reservation | `reservation` | 예약 | REL-02 `예약을 받는다` (→ MeetingRoom, N:1), REL-01 `예약한다` (→ Reserver, N:1) | BR-01, BR-02, BR-03 |
| ENT-03 | Reserver | `reserver` | 예약 | REL-01 `예약한다` (→ Reservation, 1:N) | BR-03 |

- 취소 이력은 별도 엔티티를 두지 않고 `Reservation`의 `status`·`cancelledAt`·`cancelledBy`로 남긴다(`REQ-F-005`).
- 회의실 관리 담당자는 별도 엔티티 없이 `Reserver.role`(`ROOM_MANAGER`)로 구분한다(`REQ-F-006`, `REQ-F-007`).
- 감사 컬럼은 공통 상속 방식으로 두고 개별 엔티티에 적지 않는다. 테이블 접두어는 공통 개발규칙(`4-DN-21-O3`) 확정 뒤 개정으로 반영한다.

### 3.1 문서 메타·`value_objects`·`embedded`·옵셔널 카디널리티 예시

- `meta`는 `entities.yaml` 머리에 있다(`author`·`authored_at`·`version`·`history[]`).
- 이 프로젝트에는 `value_objects`가 없다(`embedded` 사용 필드 없음).
- 옵셔널 카디널리티(`0..1:N` 등)를 쓰는 관계가 없다.
