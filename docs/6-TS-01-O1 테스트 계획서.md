## 2. 테스트 목적

요구사항 정의서(`3-AN-08-O1`)의 기능·비기능 요구사항(`구분` 열) 전체가 구현 산출물에 올바르게 반영되었는지 검증하고, UAT 서명(자체 인수 — §5.6)을 통해 시스템 인수를 확정한다. 단위·통합 테스트의 기대사항은 Backend 최종 명세서(`5-IM-23-O1`, BE)·화면 명세서(`5-IM-13-O1`, FE)가 Test-First로 이미 고정했으며 이 계획서는 그것을 인용한다.

## 6. REQ 매핑 표

> 이 표는 **계획**이다 — 각 요구사항을 어느 테스트 유형으로 덮을 것인지 정한다.
> 행은 요구사항 정의서(`3-AN-08-O1`)에서 `구분`=기능인 항목 **전체**와 `구분`=비기능 전체다.
> **실측**은 각 결과서가 기록한다: 단위는 단위 테스트 결과서(`6-TS-11-O1`) §4.1·§4.2, 통합은 통합 테스트 결과서(`6-TS-12-O1`) §3.1·§3.4, 시스템은 시스템 테스트 결과서(`6-TS-13-O1`) §3·§4(전체 케이스 표).
> 실측의 근거는 테스트 코드의 `@trace` 주석과 API 명세서의 `x-req-ids`이며, 이 계획 표가 아니다. 계획과 실측이 어긋나면 결과서가 사실이고, 계획 표를 사후 수정해 맞추지 않는다.
> 스토리 수용 기준(`US-NN.k`) 커버리지는 이 표의 분모가 아니다 — 시스템 테스트 결과서(`6-TS-13-O1`) §4가 실측한다.
> E2E 열은 `✓`만 표식으로 읽힌다(ts-15.P7).
