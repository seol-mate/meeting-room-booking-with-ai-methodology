| 컨테이너 이미지 태그 확인 | 정상 | `docker images`: `meetingroom-api:1.0.0`(ID `2b25fb484562`, 598MB) · `meetingroom-web:1.0.0`(ID `fcdf5e3a754a`, 1.6GB). 태그는 `APP_VERSION`(릴리즈 `v1.0.0`)이며, 작업 트리가 깨끗하지 않은 채 빌드해 `-dirty` 표기는 따로 붙이지 않았다 — 릴리즈 태그 확정은 7-DP-04에서 한다 |

> 검증에 쓴 스택은 확인 뒤 `docker compose --env-file .env.prod -f docker-compose.prod.yml down -v`로 내렸다(컨테이너 0개·볼륨 0개 확인). 구성 파일: `docker-compose.prod.yml`, `backend/Dockerfile`, `frontend/Dockerfile`, `.env.prod.example`.
> web 이미지가 1.6GB로 큰 것은 `next start`를 위해 전체 `node_modules`를 담았기 때문이다(`output: standalone` 미사용 — 5-IM 코드를 건드리지 않기 위한 선택). 이 규모의 개인 서비스에서는 허용한다.

| 항목 | 내용 | 연결 확인 |

| 도구 | Prometheus·Grafana 같은 별도 모니터링 도구를 두지 않는다 — Docker 자체 기능(`docker compose ps` 헬스 상태, `docker compose logs`, `docker stats`)과 Actuator `/actuator/health`를 쓴다 | 완료 |
| 수집 지표 | 컨테이너 헬스 상태(3개 서비스 healthy), api 요청 로그의 상태 코드(오류율), CPU·메모리(`docker stats`) | 완료 |
| 알림 기준 | 5xx 오류율 1% 초과(= 배포 계획서 §6 롤백 트리거와 같은 값, 이하 조건 충족). CPU·메모리·DB 커넥션 알림은 두지 않는다 — 수동 확인 | 대체 완료(자동 알림이 없어 배포 후 30분 동안 사람이 §6 명령으로 확인. 운영 인수인계서 `8-OP-01-O1`에서 점검 주기를 정한다) |
