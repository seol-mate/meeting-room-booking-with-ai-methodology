# 4-DN-21-O3 공통 개발규칙

> **Backend 구현**에 적용되는 공통 규칙을 정의한다. 모든 Backend 명세서(5-IM)는 이 문서를 참조하며, 동일한 규칙을 중복 기재하지 않는다 (Hierarchical Specification).
>
> **Frontend 공통 규칙은 이 문서가 아니다.** 프론트엔드는 공통 프레임워크 유형이 아니라 기술 스택으로 갈리며, 다음 자리에서 정한다.
>
> | 대상 | 자리 |
> |------|------|
> | FE 스택 선택 | 시스템 아키텍처 정의서(`4-DN-01-O1`) §8.1 (4-DN-03 생략) — 필수 역량은 `5-IM-01 개발환경 세팅` 참고 |
> | 선택한 구현체 기록·코딩 규칙 | `5-IM-05 코딩 컨벤션 규칙 작성` |
> | 디자인 토큰·스타일 규칙 | 디자인 컨셉 정의(`4-DN-33`) · 전체 화면 시안 작성(`4-DN-38`) |
>
> **공통 프레임워크 유형**: `1-PN-01-O1 프로젝트 개요서.md`의 기술 제약 표에서 확인한다.  
> 이 문서 하단의 프레임워크별 구현 가이드(§6) 섹션은 프레임워크 유형에 따라 분기된다.

## 2. API 응답 형식

응답 봉투(envelope) 값은 셋 중 하나다.

| 값 | 의미 | 적용 |
|---|---|---|
| `Envelope` | 기본 봉투 — `success / data / error{code,message} / meta` | `eGov`·`none` 기본값 |
| `ProblemDetail` | 봉투 없음 — 성공은 데이터 직접 반환, 오류만 RFC 9457 `ProblemDetail` | `NuriAF` 고정 |
| `없음` | 봉투 없이 스키마 본문을 그대로 응답 | `none` 프로젝트가 선택한 경우 |

프로젝트가 고른 값은 §6 `none` 절 「응답 봉투」 행에 적는다(`NuriAF`는 자동으로 `ProblemDetail`). 하류(5-IM)는 이 값을 따른다. **이 프로젝트의 값은 `Envelope`다.**

**스키마 이름은 `Envelope`(응답 봉투)·`ValidationError`(검증 오류 항목)로 통일한다** — API 명세서(`5-IM-12-O1`) `components.schemas`가 이 이름으로 정의하므로, 프로젝트가 임의로 다른 이름(`ApiResponse`·`FieldError` 등)을 쓰지 않는다.

**봉투 인스턴스 생성은 정적 팩토리 메서드(`Envelope.ok(data)` 등)보다 DI 빈(예: `EnvelopeFactory`)을 쓴다** — 봉투에 `Clock`·MDC `requestId` 등 요청 컨텍스트 값을 채워야 하는 경우 정적 팩토리는 그 값에 접근할 수 없다. 컨텍스트 값이 필요 없는 단순 봉투라면 정적 팩토리로도 충분하며, 이 경우 프로젝트가 선택한 형태를 코딩 컨벤션 규칙(`5-IM-05-O1`) §2 「봉투 생성 방식」 행에 기록한다.

공통 원칙(프레임워크 무관): 모든 응답은 성공/실패 여부·데이터·오류 정보를 프레임워크가 정한 형식으로 일관되게 전달하고, 검증 오류는 항목별(`field`·`value`·`reason` 등)로 식별 가능하게 전달한다.

## 3. 페이징 규칙

페이징이 필요한 목록 API는 아래 파라미터와 응답 구조를 따른다.

**요청 파라미터**

| 파라미터 | 타입 | 기본값 | 설명 |
|---------|------|--------|------|
| page | integer | 1 | 조회할 페이지 번호 (1부터 시작) |
| size | integer | 20 | 페이지당 항목 수 (최대 100) |
| sort | string | — | 정렬 기준 컬럼명 |
| direction | string | ASC | 정렬 방향 (ASC \| DESC) |

**응답 data 구조 (목록)**

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "size": 20,
    "totalCount": 150,
    "totalPages": 8
  }
}
```

**정렬(`sort`) 매핑** — 기본적으로 엔티티의 정렬 가능 속성에 매핑한다. 엔티티가 없는 조회 모델(네이티브 SELECT 프로젝션 등)은 그 조회 모델의 별칭(alias)을 정렬 기준으로 허용한다 — 엔티티 필드명 강제는 이런 조회에서 성립하지 않는다.

## 4. 예외 처리 규칙

> 아래 `ERR-` 오류 코드 체계는 §2 값이 `Envelope` 또는 `없음`인 프로젝트에 적용한다(`eGov`·`none` 기본값). `NuriAF`는 프레임워크의 `ErrorCode` 열거형 + RFC 9457 `ProblemDetail`이 정본이며(§6 NuriAF 절, dev-guide 03) 이 표를 재정의하지 않는다 — HTTP 상태 코드 구분 원칙(400/422/500)과 아래 불릿은 프레임워크와 무관하게 적용한다. `[고도화]`·`[유지보수]`에서 편입 코드의 상태 코드 배정(기준 커밋에서 대조한 값)이 이 표와 다르면 편입 값을 따르고 이 절에 이탈과 근거를 적는다 — 편입은 코드가 정본이며, 같은 성격의 실패가 편입·변경분 API에서 갈리지 않게 변경분도 같은 값을 쓴다.

| HTTP 상태 코드 | 오류 코드 | 사용 상황 |
|--------------|----------|---------|
| 400 | ERR-4000 | 필수 파라미터 누락 또는 형식 오류 |
| 401 | ERR-4010 | 인증되지 않은 요청 |
| 403 | ERR-4030 | 접근 권한 없음 |
| 404 | ERR-4040 | 요청한 리소스가 존재하지 않음 |
| 409 | ERR-4090 | 리소스 충돌 (예: 중복 등록) |
| 422 | ERR-4220 | 비즈니스 규칙 위반 (유효성 검사 통과 후 도메인 오류) |
| 500 | ERR-5000 | 서버 내부 오류 (스택 트레이스는 로그에만 기록) |

- 예외 발생 시 스택 트레이스를 API 응답 본문에 포함하지 않는다.
- 비즈니스 오류(422)와 시스템 오류(500)를 구분하여 처리한다.
- 입력값 유효성 오류는 400으로 처리한다. 항목별 설명을 담는 위치는 §2 값을 따른다 — `ProblemDetail`이면 `errors[]`의 각 항목(`field`·`value`·`reason`), `Envelope`이면 `error.message`(항목별은 `ValidationError` 배열), `없음`이면 응답 본문 최상위 `errors[]`.

**이 프로젝트의 적용** — 업무프로세스 정의서(`3-AN-09-O1`) 예외 흐름(`EX-`)의 시스템 응답을 위 상태 코드에 이렇게 배정한다.

| 상황 | 상태 코드 | 근거 |
|------|----------|------|
| 입력 오류(로그인 정보·회의실 정보·조회 기간 형식) | 400 ERR-4000 | EX-RSV-01, EX-MTR-01, EX-MTR-04 |
| 로그인하지 않은 요청 | 401 ERR-4010 | REQ-NF-001, EX-RSV-02, EX-RSV-04, EX-MTR-05 |
| 권한 없음(관리 담당자 전용 기능) | 403 ERR-4030 | EX-RSV-11, EX-MTR-02 |
| 예약 시간 겹침 | 409 ERR-4090 | BR-01, EX-RSV-08 |
| 시간 단위·길이 위반, 시작 이후 취소 | 422 ERR-4220 | BR-02, EX-RSV-07, EX-RSV-10 |
| 저장·조회 실패(시스템 장애) | 500 ERR-5000 | EX-RSV-03, EX-RSV-05, EX-RSV-09, EX-RSV-12, EX-MTR-03, EX-MTR-06 |

## 5. 로깅 규칙

| 레벨 | 사용 기준 |
|------|---------|
| INFO | API 요청 수신, 정상 처리 완료, 외부 시스템 연동 결과 |
| WARN | 재시도 가능한 오류, 예상 범위의 비정상 입력 |
| ERROR | 처리 불가 오류, 외부 연동 실패, 데이터 정합성 이상 |
| DEBUG | 개발 환경 전용. 운영 환경에서는 비활성화한다. |

- 모든 API 요청 로그에 `requestId`를 포함하여 추적 가능하게 한다 (End-to-End Traceability).
- 개인정보(이름, 연락처, 주소 등)는 로그에 평문으로 기록하지 않는다. 비밀번호와 비밀번호 해시는 어떤 레벨에도 기록하지 않는다.
- 로그 형식: `[레벨] [requestId] [클래스명.메서드명] 메시지`

## 6. 프레임워크별 구현 가이드

> `config.yaml`의 **`project.framework`**에 따라 아래 분기 중 해당하는 하나를 채운다(품질 게이트 dn-21.P9). 값은 `NuriAF` / `eGov` / `none` 셋뿐이며 각각 아래 세 절과 1:1로 대응한다.
> (`1-PN-01-O1` §6 공통 프레임워크·킥오프 결정 `D-`와 같은 값이다. 다르면 킥오프 결정을 확인해 config를 맞춘다.)
> **해당하지 않는 절은 프로젝트 기재 칸을 지우지 않고 「해당 없음 — {실제 project.framework 값} 프로젝트」 한 줄로 접는다**(예: `NuriAF` 프로젝트라면 `eGov`·`none` 절에 각각 「해당 없음 — NuriAF 프로젝트」) — 절 자체를 지우면 다른 절이 참조하는 기본값 정의가 사라진다. 자리표시자 `{framework}`를 그대로 남기지 않는다.
>
> 이 분기는 **백엔드 공통부** 기준이다. 기술 스택(Spring Boot·React 등)으로 갈리지 않는다.

해당 없음 — none 프로젝트

---

### `eGov` — 전자정부 표준 프레임워크 기반

해당 없음 — none 프로젝트

### `none` — 표준 공통 프레임워크 없음 (자체 개발)

사내·공공 표준 공통 프레임워크를 쓰지 않고 공통부를 직접 만드는 경우다.
Spring Boot·NestJS 등 어떤 기술 스택을 쓰든, 공통부를 프로젝트에서 정의한다면 여기에 해당한다.
아래 항목을 프로젝트 초기에 정의하고 이 문서에 직접 기재한다. **각 항목의 기본값은 특별한 사유가 없으면 그대로 채택**하고, 프로젝트가 다르게 정하면 그 내용으로 대체 기재한다(빈 칸으로 승인 요청하지 않는다).

| 정의 항목 | 내용 (기본값 — 다르게 정하면 대체 기재) |
|---------|------|
| 응답 봉투 | `Envelope`(기본값 채택) — `success/data/error{code,message}/meta`, 검증 오류는 `error.message`에 포함하고 항목별은 `ValidationError` 배열 |
| 패키지 구조 | 모듈 경계·허용 의존은 소프트웨어 아키텍처 정의(`4-DN-03`) 생략으로 기본값(단일 모듈)을 따른다. 레이어드: 루트 패키지 아래 `domain.reservation`·`domain.meetingroom`(도메인별 `controller`·`service`·`repository`·`entity`·`dto`) + `common`(`config`·`exception`·`util`). 루트 패키지 접두는 미확인 — 확인 필요(수행 조직 미정, 개발환경 세팅 5-IM-01에서 확정). 도메인 우선·레이어 하위 구조로 도메인 단위 응집을 유지한다 |
| 네이밍 규칙 | 기본값 채택 — Java 표준: 클래스 PascalCase, 메서드·변수 camelCase, 상수 UPPER_SNAKE, 패키지 소문자. 접미어 `XxxController`·`XxxService`·`XxxRepository`·`XxxEntity`·`XxxRequest/XxxResponse`(DTO). DB 테이블·컬럼은 snake_case이고 **테이블 접두어는 쓰지 않는다**(`entities.yaml`의 `table`과 일치). 상세는 Google Java Style Guide 준용 |
| Controller 규칙 | 기본값 채택 — 요청 검증(`@Valid`)·응답 봉투 변환만 담당. 비즈니스 로직 금지. 반환은 공통 응답 봉투로 통일, 예외는 GlobalExceptionHandler에 위임. 단건 조회·등록/수정 응답처럼 Repository가 엔티티를 반환하는 경우에만 `from(entity)`로 변환한다 |
| Service 규칙 | 기본값 채택 — 비즈니스 로직·트랜잭션 경계(`@Transactional`)를 담당. Controller의 HTTP 타입(HttpServletRequest 등)에 의존하지 않는다. 도메인 간 호출은 Service 레이어에서만(예: 회의실 서비스가 예약 서비스를 호출) |
| Repository 규칙 | **데이터 접근 기술은 시스템 아키텍처 정의서(`4-DN-01-O1`) §8.1 「데이터 접근」 행(JPA)을 따른다.** 공통: 데이터 접근 전담, 비즈니스 판단 금지. 목록 조회는 프로젝션 DTO를 직접 반환한다(엔티티를 거치지 않는다). `[JPA]` 기본값 채택: Spring Data JPA 인터페이스 + 복잡 쿼리는 QueryDSL/@Query, N+1은 fetch join·EntityGraph로 해소. 잠금 규칙은 아래 「Repository 잠금 규칙」 참조 |
| 공통코드 관리 방식 | **Enum** — 선택 기준: 예약 상태·역할 코드는 배포 시점에 고정되고 코드 관리 화면이 없다(사이트맵 `4-DN-31-O1` 확인). 코드 정의서(`4-DN-21-O2`) §1의 `공통코드 관리 방식` 행과 같다 |
| 도메인 이벤트 규약 | 기본값 채택 — 도메인 이벤트를 쓰지 않는다(도메인 간 호출은 Service 레이어 동기 호출만). 아키텍처 정의서(`4-DN-01-O1`) §5도 도메인 이벤트 없음으로 일치한다 |

**Repository 잠금 규칙 (`[JPA]`)** — 비관적 잠금을 쓰는 경우의 기본값이다.

- 잠금 후 최신 상태를 다시 읽어야 하면 `em.refresh(entity, LockModeType.PESSIMISTIC_WRITE)`를 쓴다 — JPA 1차 캐시 때문에 `@Lock` 지정 JPQL로 재조회하는 것만으로는 엔티티 상태가 갱신되지 않는다.
- 잠금 대상은 **Aggregate 루트 일반형**이다(`entities.yaml`의 `aggregate_root`로 식별되는 엔티티) — 자식 엔티티를 개별로 잠그지 않는다.
- PostgreSQL은 `lock.timeout` 힌트를 반영하지 않는다 — `SET lock_timeout`(세션 GUC)으로 대신하고, 커넥션 풀 초기화로 걸면 풀 수명 동안 유지되므로 장시간 배치는 풀을 분리한다.
- 예약 시간 겹침(`BR-01`)은 서비스 계층 검사에 더해 DB 배제 제약(`ex_reservation_overlap`, `4-DN-14-O2-reservation` §6)이 최종으로 거부한다 — 제약 위반 예외를 409 `ERR-4090`으로 변환한다.

> 위 기본값으로 채우기 어려운 세부(예: 프로젝트 고유 레이어)는 시스템 아키텍처 정의서(`4-DN-01-O1`) §8.1의 결정을 근거로 조정한다.
